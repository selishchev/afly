## afly — AppsFlyer → ClickHouse extractor

This workspace contains one or more **afly** projects. afly is a dbt-style
Python tool that idempotently pulls AppsFlyer aggregate Pull API reports and
writes them into ClickHouse via a `load → idempotent write` pipeline, driven
by the `afly` CLI. A directory is an afly project when it contains an
`afly_project.yml` file.

**Help the user operate afly**: configure extracts, run backfills, debug a
failing pull, reason about quota budgets, and understand why a day's data
looks the way it does. Extracts are declarative YAML; there is no Python to
write for a normal task.

### Skills

- **First-time setup** — use the **`afly-setup-project`** skill: `afly init`
  scaffolds a project with placeholder credentials; this skill walks you
  through `.env`, `afly validate`, `afly debug`, and a `--dry-run` before the
  first real pull.
- **A new extract** — use the **`afly-new-extract`** skill: it picks
  `report_type`/`category`/`media_source`, checks for double-counting against
  sibling extracts (the `exclude_media_sources` ownership convention), and
  validates the result.
- **A backfill** — use the **`afly-backfill`** skill: it sizes `--chunk-days`
  and `--max-calls` against the AppsFlyer quota so a wide `--from/--to` window
  doesn't blow the daily long-call budget, then verifies the result against
  `_afly_loads`.
- **A run failed, or looks wrong** — use the **`afly-debug-run`** skill: reads
  `_afly_loads` for failed/skipped chunks, tells a quota skip from a real
  failure from the empty-response guard, clears a stuck lock, and uses
  `afly debug --pull` to diagnose a CSV-shape problem.

### Gotchas that bite (keep these in mind)

- **The Facebook split is a config concern, not a bug.** AppsFlyer only
  returns campaign/adset/adgroup columns for a Facebook-*scoped* pull
  (`media_source: facebook`), so the scaffold ships a separate `facebook`
  extract and excludes Facebook from the unfiltered `standard` one
  (`exclude_media_sources: [Facebook Ads]`). Forgetting the exclusion
  double-counts Facebook spend across two extracts writing the same table.
  Same pattern for any other media source pulled by its own extract (e.g.
  `yandex`) — see `formats.md`.
- **Quota tiers, and why `chunk_days: 2` is the default.** A pull spanning
  fewer than `quota.long_call_min_days` (default 3) days is a "short" call —
  throttled per-minute, no daily cap. 3+ days draws down a small daily budget
  per account/app. Widening `chunk_days` on a backfill can silently exhaust
  that budget for the day; see `quotas.md` before hand-tuning it.
- **An empty AppsFlyer response is not applied over existing data**
  (`on_empty: skip`, the default). A day that already has rows for an
  (extract, app) pair keeps them if a re-pull comes back empty — this
  protects against a transient AppsFlyer hiccup silently wiping history.
  Override with `on_empty: replace` on the extract, or `--allow-empty` for
  one run.
- **Never hand-edit an afly destination table, and never `ALTER` it
  yourself.** afly creates and evolves its own tables — if a schema check
  finds a real drift, `afly debug`/`afly run` prints the exact `ALTER TABLE`
  statement to run; afly deliberately never runs it for you. The
  `<table>__afly_staging` table is afly's own scratch space for the
  partition-rebuild write path (`idempotency.md`) — don't write to it, don't
  rely on it existing between runs.
- **`_afly_loads` / `_afly_locks` are internal bookkeeping**, not part of the
  destination schema — read them for diagnostics (`idempotency.md`), never
  join them into a report.
- **Credentials only via environment variables.** `profiles.yml` never holds
  a literal token/password/webhook URL — always `${VAR}` or
  `{{ env_var('VAR') }}`, resolved from the shell/`.env` at load time. Never
  paste a real credential into a YAML file or into chat.
